# AI SSD 测试用例说明（管理层版）

**版本**：1.0

**适用对象**：需要做产品选型、项目评审、客户沟通或发布决策，但不需要先掌握 AI 存储框架的管理人员

**配套文件**：[AI SSD 测试用例补充说明](AI_SSD_TEST_CASES_SUPPLEMENT.md)
**详细执行依据**：[AI SSD 场景测试方案](AI_SSD_TEST_PLAN.md)、[消费级 AI PC 多阶段测试方案](AI_PC_CONSUMER_SSD_MULTI_STAGE_TEST_PLAN.md)

## 1. 先看结论

AI SSD 不是“顺序读写带宽越高越好”。真正要回答的是：

1. 训练数据能不能稳定供应给计算任务，SSD 会不会让训练等待。
2. 大模型保存和恢复时，SSD 能不能在规定窗口内完成，并且数据不损坏。
3. KV Cache 溢出到 SSD 后，用户等待时间是否仍然可接受。
4. 本地知识库建库、搜索和后台整理同时发生时，搜索质量和响应速度是否稳定。
5. 多种 AI 任务共用一块 SSD、盘快满或温度升高后，性能会不会明显下降。

因此，最终报告不建议给一个无法解释的“AI SSD 总分”，而应给出五张成绩单：

| 成绩单 | 对应业务问题 | 最重要的结果 |
|---|---|---|
| 训练供给 | SSD 会不会拖慢训练 | 达到训练质量门槛时的样本吞吐、等待比例 |
| Checkpoint | 保存/恢复是否及时可靠 | 最慢分片完成时间、恢复时间、数据完整性 |
| KV Cache | 大模型并发用户是否稳定 | 最大合格用户数、P95/P99/P99.9/P99.99 |
| VectorDB/RAG | 本地知识库是否又快又准 | Recall 达标后的 QPS 和尾延迟 |
| 共存与长期运行 | 日常使用是否互相影响 | 前台延迟放大、后台吞吐保持率、温度和错误 |

## 2. 测试用例到底在测什么

### 2.1 训练数据读取

训练时，模型不断从存储读取数据。如果 SSD 供给不稳定，计算设备会“等数据”。

| 代表场景 | 可以类比成 | 主要观察 |
|---|---|---|
| UNet3D | 少量大文件持续搬运 | 持续读带宽、训练利用率、每轮稳定性 |
| RetinaNet | 大量小图片逐个打开 | 文件操作速度、IOPS、尾延迟、CPU 开销 |
| ResNet50/CosmoFlow | 中等大小文件和批量读取 | 并发读取、随机性、队列变化 |
| DLRM/Flux | 只读取 Parquet 中需要的列或分组 | 有效数据率、预取、CPU 与 SSD 的平衡 |

管理层应重点看：达到规定训练质量后，样本吞吐是否稳定；而不是只看 SSD 标称 GB/s。

### 2.2 Checkpoint 保存和恢复

Checkpoint 可以理解为“给正在运行的大模型保存进度”。它通常是一次较大的并发写入，恢复时又要快速读取多个分片。

管理层应关注：

- 保存窗口是否满足业务要求；
- 最慢的分片是否拖住所有进程；
- 机器重启或清除缓存后，恢复是否仍然快；
- 文件大小、校验和和恢复结果是否完全一致。

如果只测“写文件成功”，不能说明 SSD 具备可靠的 Checkpoint 能力。

### 2.3 KV Cache 下沉

大模型对话过程中会产生 KV Cache。显存和内存不足时，这些数据会下沉到 SSD；SSD 变慢会直接表现为用户响应变慢。

| 选项 | 含义 | 管理层应看 |
|---|---|---|
| Option 1 | 主要使用 SSD，压力最大 | 并发用户数、尾延迟、SSD 实际读写 |
| Option 2 | 先使用约 4 GB CPU 内存，再溢出到 SSD | 溢出发生的时间和发生后的延迟变化 |
| Option 3 | 更大的模型对象、较低并发 | 单次对象服务时间、带宽和恢复能力 |

平均响应时间不够。必须看 P95、P99 甚至 P99.99，因为少数最慢请求往往决定用户是否觉得系统“卡”。

### 2.4 VectorDB / RAG

本地 RAG 系统通常要先导入向量、建立索引，再持续搜索。SSD 可能参与建库、索引、加载、后台整理和在线查询。

结果必须同时满足两件事：

1. 搜索结果质量达到 Recall 门槛；
2. 在这个质量门槛下，比较 QPS 和响应尾延迟。

不能通过降低搜索质量来换取更高 QPS。

### 2.5 共存、热稳定和恢复

真实设备很少只运行一项任务。典型组合包括：训练读取 + Checkpoint 写入、KV 查询 + Checkpoint 写入、RAG 搜索 + 建库整理。

这部分回答的是：“一项任务变忙时，会不会把另一项任务拖垮？”同时观察高占用率、SLC 缓存耗尽、垃圾回收、温度升高、重启和异常后的行为。

## 3. 用例等级：哪些结果可以用于决策

现有材料中的 Case 有不同的结论范围，不能混在一起比较：

| 类型 | 说明 | 可以支持的结论 |
|---|---|---|
| Native | 真实应用、真实路径、真实 DUT | 可作为主要产品结论 |
| Scaled | 工作集或模型按比例缩小 | 可做条件性结论，必须写明缩放比例 |
| Trace/Replay | 回放逻辑读写节奏 | 可分析 SSD 能力曲线，不能冒充完整应用成绩 |
| Hybrid | 应用和回放组合 | 用于归因分析，须与 Native 分开发布 |

建议把 33 个直接 native Case 和 17 个核心 + 3 个可选 consumer native Case 作为当前执行集合；72 个完整场景矩阵只作为扩展分析池。低容量设备不能因为跑不了 TB 级 Case 就被记为“性能为零”；应标为容量不适用或 `NOT RUN`。

## 4. 管理层如何阅读一份结果

一份结果至少要回答以下六个问题：

| 问题 | 合格证据 |
|---|---|
| 测的是不是目标 SSD | 数据、缓存、Checkpoint 和数据库卷都有物理盘映射；结果目录与 DUT 分离 |
| 测的是不是目标 workload | 模型、数据规模、并发、随机种子和执行模式完整记录 |
| SSD 是否真的被访问 | 逻辑字节与物理磁盘字节有时间对齐证据 |
| 结果是否稳定 | 至少三次有效运行，给出中位数、波动和最差窗口 |
| 结果是否正确 | 文件数、hash、Checkpoint restore、Recall 或 KV 命中校验通过 |
| 失败原因是什么 | 区分 SSD 瓶颈、CPU/内存瓶颈、缓存命中、温度降速和容量不足 |

出现以下任一情况时，结果不应进入产品排名：路径未命中 DUT、缓存状态不明、缺少关键监控、缺 rank/trial、数据校验失败，或把 Scaled/Replay 当成 Native。

## 5. 推荐的管理决策页面

每一块 SSD 最终建议用一页汇总，而不是直接展示几十行 Excel：

| 维度 | 建议展示 | 决策含义 |
|---|---|---|
| 业务能力 | 训练、Checkpoint、KV、RAG、共存五项状态 | 是否满足目标产品场景 |
| 性能 | 主指标中位数、P95/P99、最差窗口 | 平均快不等于体验稳定 |
| 容量 | 工作集、剩余空间、填充率、是否 Scaled | 结果是否适用于目标容量 |
| 稳定性 | 温度、降速、性能漂移、错误计数 | 长时间使用是否可控 |
| 正确性 | hash、恢复、Recall、KV 命中 | 快但不可靠的设备不能通过 |
| 风险 | 未运行项目、假设、主机瓶颈、工具限制 | 结论边界和后续投入 |

推荐使用“通过 / 有条件通过 / 不通过 / 无效 / 未运行”五种状态，而不是用一个分数掩盖证据缺口。

## 6. 管理层需要特别警惕的误读

- 标称顺序带宽高，不代表小文件、KV 尾延迟或混合负载好。
- 应用报告的逻辑读取量，不等于 SSD 实际读取量；页缓存可能让结果虚高。
- 1K 向量库的 smoke 结果只能证明链路可运行，不能代表百万级 ANN 性能。
- 70B/405B/1T 的 Scaled 或 Replay 结果不能表述为本机完整运行能力。
- 模拟 accelerator 数量是 I/O 压力模型，不是 GPU 性能排名。
- 单次峰值不能代表持续性能；必须看稳定窗口、温度和后半程退化。

## 7. 最终建议

现有 Case 数量已经足够支撑第一轮产品判断。下一步最有价值的工作是：

1. 自动把业务指标和完整性检查写入最终 verdict；
2. 固定 SSD 的预处理、填充率、温度和缓存状态；
3. 让混合负载真正并发，并完整采集前台尾延迟；
4. 把 Native、Scaled、Replay 分开出成绩单；
5. 在条件允许时增加一个真实模型权重加载或 GPU 推理锚点。

技术术语、门槛和执行细节见[补充说明文档](AI_SSD_TEST_CASES_SUPPLEMENT.md)。
